# GPU 显存与多服务共存原理

> 核心问题：一张显卡能不能同时跑 LLM 和生图两个服务？答案取决于显存，而显存机制有很多反直觉的地方，先讲原理。

## 算力可以共享，显存是独占的

- **算力（SM）可时间片共享**：多个进程能同时"占用" GPU 轮流算，只是互相拖慢。llama-server 空闲时利用率 0%，完全不碍事。
- **显存（VRAM）是独占的**：一个进程分配出去的显存，另一个进程用不了。这是所有共存问题的根源。

## 消费级卡不是"不能共享显存"，是"不支持 MIG 硬分区"

MIG（Multi-Instance GPU）是 A100/H100 等数据中心卡才有的硬分区：把 GPU 切成多个完全隔离的实例，各自固定显存/算力配额，一个实例 OOM 不影响另一个。**GeForce 全系都没有 MIG**。

但**所有 NVIDIA 卡（含消费级）原生支持多进程共享一块卡**——CUDA 的显存是动态分配的：

| 机制 | 行为 |
|---|---|
| 多进程并发 | ✅ 一直可以（llama-server + ComfyUI 同时跑没问题） |
| 显存分配 | 谁先申请谁先拿，动态分配 |
| 显存不够时 | ❌ 分配失败 = **OOM 崩溃**（不是自动降级！） |

所以真正的问题不是"支不支持分区"，而是 **两个进程的显存峰值总和 ≤ 物理显存（且留 1-2G 余量）**。

## offload 不是 CUDA 自动做的，是应用自己实现的策略

显存不够时"借用 CPU 内存"这件事，分成两层，行为完全不同：

```
CUDA 层面： 谁申请谁拿，申请不到 = OOM 崩溃
    ↓
llama.cpp： 加载时按 -ngl 参数【静态分配】。
            显存不够 → 直接报错退出，不会自动转 CPU
            （-ngl 40 = 指定 40 层放 GPU，其余放 CPU，加载时就定死）
    ↓
ComfyUI：   【动态策略】。启动时探测剩余显存，自动决定：
            够 → 模型全上卡（NORMAL）；不够 → 自动把部分层 offload 到 CPU（慢但能跑）
```

**关键差别**：llama-server 是"静态的、占多少由参数决定、不够就报错"；ComfyUI 是"动态的、自己探测、不够就自动降级"。

## ComfyUI 空闲时几乎不占显存

- ComfyUI 有 dynamic VRAM loading：**模型不是常驻的**，只在任务执行时搬进显存，跑完可以释放。
- 空闲时只占 ~0.3G（CUDA context）。
- 所以"共存"的实际形态是：**LLM 常驻占显存 + ComfyUI 按需借用剩余空间**，不是两个大块头永远挤在一起。

## 共存实例：显存预算账（我们场景）

```
llama-server（27B Q4，-ngl 40）  常驻 ~9.8G
ComfyUI 空闲                    ~0.3G
ComfyUI 跑 qwen-image 峰值      ~11G（9.1G 权重 + CLIP/VAE/中间激活）

24G 卡峰值合计 ≈ 21G ✅ 留 3G，全速无 offload
16G 卡峰值合计 ≈ 21G ❌ 装不下
```

**部署顺序建议**：llama-server 先启动（静态分配，若显存不够会直接报错）→ ComfyUI 后启动（动态探测剩余空间，自适应）。

## 剩下的"竞争"：算力与带宽

即使显存装得下，两个服务同时真忙时（LLM 正在生成 + ComfyUI 正在采样）会抢 SM 算力和显存带宽，互相拖慢——消费级卡无法用参数消除。但聊天是间歇性的、生图是任务式的，同时忙的概率低，影响可接受。
