# 公网暴露方案：怎么让同事/他人访问到我们的生图服务

> 背景：生图服务跑在 AutoDL 云 GPU 实例上。平时我们用 SSH 隧道（本机 `localhost:8080` → 服务器 8080）自用。
> 但**同事没有我们的 SSH 凭据**，想要他们也能访问，就必须把服务暴露到公网。
> 本文记录三条路线（A/B/C）的原理、适用场景与选择建议，重点是 B 和 C —— 这两个以后会经常遇到。

## 一、先理解 AutoDL 的网络模型（关键前提）

AutoDL 实例**没有独立公网 IP**：

```
AutoDL 实例（容器） ──► AutoDL 平台网关（共享出口） ──► 公网
                        ↑
                  所有实例共用一个出口 IP
```

带来的限制：

| 事实 | 说明 |
|---|---|
| 实例内服务只能监听内网端口 | 如 8188 / 8190 / 8080，外部不可直连 |
| 平台默认只映射 6006、6008 两个端口 | 每个实例有专属公网地址（控制台「自定义服务」查看）|
| 开放**任意**端口需**企业认证** | 个人用户无法开放 6006/6008 之外的端口 |
| 出站（实例→公网）不受限 | 实例可以主动访问任何公网地址 —— 这是方案 C 的基础 |

> 经验：**"没有公网 IP / 入站受限"是云 GPU 平台（AutoDL、恒源云等）的普遍形态**，
> 因为它们按 GPU 计费，公网 IP 和带宽是额外成本。这类机器想对外提供服务的通用解法就是方案 C（反向隧道）。

## 二、方案 A：AutoDL 开放自定义端口（❌ 本项目不可用）

- 原理：在 AutoDL 控制台做企业认证后，可开放任意端口，获得公网地址 `https://xxx.seetacloud.com:8080`
- 适用：有企业资质的团队
- 本项目：**个人无企业认证，直接排除**

## 三、方案 B：用 AutoDL 自带的 6006/6008 端口转发（✅ 最快，个人可用）

### 原理

AutoDL 为每个实例**预置** 6006 和 6008 两个端口的公网映射：

```
公网 https://u39-xxxx.seetacloud.com:8443  （控制台「自定义服务」查看具体地址）
   │  平台网关转发
   ▼
实例内 6006 端口  ← 我们把 nginx 服务挂到这里
```

### 做法（在实例内）

1. 控制台「自定义服务」入口，查看 6006 映射出来的公网地址（如 `https://u39-xxx.nmb2.seetacloud.com:8443`）
2. 让 nginx 额外监听 6006（或在 6006 上跑一个转发服务），把流量导到后端 8190
3. 把公网地址 + Basic Auth 密码发给同事

### 优缺点

| 优点 | 缺点 |
|---|---|
| 零成本、免认证、几分钟搞定 | 端口固定（只有 6006/6008 两个）|
| 地址相对稳定 | 地址是 AutoDL 的域名，不归我们管 |
| | 6006 是平台默认开放，理论上被扫描到也能访问（靠 Basic Auth 挡）|

### 本项目适用性

私下发给几个认识的人：**够用**。Basic Auth 已配好，直接复用。

## 四、方案 C：frp 反向隧道（✅ 通用做法，推荐长期方案）

### 为什么通用

frp（Fast Reverse Proxy）解决的本质问题是：**一台没有公网入站的机器（AutoDL），如何让公网用户访问到它上面的服务**。
答案：让这台机器**主动出站**连一台有公网 IP 的机器，建立隧道，反向暴露端口。

> 这是内网穿透的通用解法，适用于：AutoDL 云 GPU、家里 NAS、公司内网服务器……任何"能上网但没公网 IP"的机器。
> 同类工具：frp、ngrok、cloudflared、tailscale（funnel）等。frp 自建可控，最适合我们。

### 架构

```
用户浏览器
   │  域名 / 公网 IP
   ▼
腾讯云（有公网 IP，跑 frps = frp server）
   │  端口 8080 收到请求
   │       ↓ frp 隧道
   ▼
AutoDL 实例（跑 frpc = frp client，主动连出到腾讯云）
   ▼
nginx:8080（Basic Auth）→ FastAPI:8190 → ComfyUI:8188 → GPU
```

- **frps（server）**：跑在腾讯云，监听一个端口（如 7000 管隧道、8080 对外服务）
- **frpc（client）**：跑在 AutoDL，启动时主动连 frps，声明"把本机 8080 映射到 frps 的 8080"
- 关键：AutoDL **出站不受限**，所以 frpc 能连出去；入站需求被隧道解决，AutoDL 无需开放任何入站端口

### 进阶：前端也放腾讯云

既然腾讯云有公网 IP + nginx，可以把**前端页面也部署在腾讯云**，形成完整闭环：

```
用户 → 腾讯云前端页面（域名/IP）
              │  JS 调 /api/*  （腾讯云 nginx 反代）
              ▼
      腾讯云 frps → 隧道 → AutoDL 后端
```

好处：用户只接触腾讯云一个入口，不需要知道 AutoDL 存在；域名、HTTPS、限流都在腾讯云做。

### 优缺点

| 优点 | 缺点 |
|---|---|
| 通用，任何无公网机器都能用 | 需要一台有公网 IP 的机器（腾讯云 ~10ms 延迟，本项目已有）|
| 入口完全可控（端口/域名/HTTPS 随我们定）| frp 本身不加密（可用 HTTPS 或 frp 的 TLS 补）|
| 不依赖 AutoDL 平台特性 | 多一跳，略有延迟（本地到腾讯云 + 隧道到 AutoDL）|

### 本项目现状

- 已有腾讯云服务器（公网 IP 见 AGENTS.md 情报，免密 SSH）
- 腾讯云已跑 nginx（443/80）
- 待办：腾讯云装 frps + AutoDL 装 frpc + 前端部署，即可对外提供访问

## 五、方案对比与选择

| 维度 | A 开放端口 | B 6006/6008 | C frp 隧道 |
|---|---|---|---|
| 个人可用 | ❌ 需企业认证 | ✅ | ✅ |
| 成本 | — | 0 | 需一台公网机器（已有）|
| 地址可控 | 部分 | ❌ AutoDL 域名 | ✅ 我们的 IP/域名 |
| 通用性 | 仅 AutoDL | 仅 AutoDL | **任何无公网机器** |
| 本项目决策 | 排除 | 临时应急 | **长期方案** |

## 六、安全与认证（不管用哪个方案都要想清楚）

- **公网 ≠ 私发**：暴露到公网的那一刻起，扫描机器人就会来。任何方案都必须保留认证，哪怕是发给熟人
- 本项目现状：nginx Basic Auth（`comfy/密码`）—— 轻量够用；真开放公网可加 HTTPS 防明文
- 后续可升级：邀请码 / token / 用户系统（见 `docs/backlog.md` 思路）
