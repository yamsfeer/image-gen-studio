# 显存调度方案：ComfyUI ↔ llama-server 切换机制

> 状态：**设计文档（未实现）**。本文记录问题背景、已确认的技术能力、方案设计与待决策点。
> 等完整的「显卡资源调度器」设计定稿后再实现。

## 一、问题背景

同一台 4090 24GB 上跑两个 GPU 服务，**无法同时运行**（已实测，显存不足）：

| 服务 | 显存占用 | 加载方式 |
|---|---|---|
| llama-server（Qwen3.8-27B，另一个 AI 进程管理）| ~17GB | 启动即常驻显存 |
| ComfyUI（生图，我们管理）| 模型加载后 ~8-15GB | **仅出图时加载**，空闲时不占（但加载后不会自动卸）|

矛盾点：
- 两个服务**同时加载模型** → 显存不够
- 即使勉强运行（借内存）→ 速度大幅下降，不可接受
- 但两个服务都**需要能用**（聊天 + 生图）

## 二、已确认的技术能力（重点：我们有主动权）

通过实测 ComfyUI 源码，确认了两个可控手段：

### 1. ComfyUI `/free` 接口 —— 卸载模型，进程保留

```
POST http://127.0.0.1:8188/free
{"unload_models": true, "free_memory": true}
```

- 源码位置：ComfyUI `server.py` 1192-1200 行（`post_free`）
- 作用：设置 `unload_models` / `free_memory` 标志，**在下一个 prompt 前卸载模型、释放显存**
- 特点：进程保持运行，重新加载模型快（~10 秒级）；但释放动作依赖下一次任务触发，不是立即回收

### 2. 杀死 ComfyUI 进程 —— 彻底让出显存

```
pkill -f "[m]ain.py --listen"    # 或按 PID kill
```

- 作用：ComfyUI 退出，显存 100% 还给系统（llama-server 可用）
- 代价：下次生图要重新启动 ComfyUI + 加载模型（~40 秒）
- 重启方式：`/root/image-service/autorecover.sh`（已实现开机自启，同样可手动触发）

### 3. 服务层自动拉起能力（已具备）

`autorecover.sh` 幂等：检查三个服务（ComfyUI/服务层/nginx），死了就拉起。
服务层（FastAPI）可以调用它，实现「生图请求进来时 ComfyUI 不在 → 自动拉起」。

## 三、方案设计（草稿，待定稿）

### 核心思路：懒加载 + 显存让渡

```
生图请求 → 服务层检查 ComfyUI 活着吗？
            ├─ 活着 → 直接用
            └─ 死了 → 自动拉起 → 等就绪 → 提交任务
```

### 计划新增的接口（加到 FastAPI 服务层）

| 接口 | 作用 | 实现 |
|---|---|---|
| `POST /comfyui/unload` | 卸载模型释放显存（进程保留）| 调 ComfyUI `/free` |
| `POST /comfyui/exit` | 完全退出 ComfyUI（显存全还）| kill 进程 |
| `POST /comfyui/autorestart` | 设置开关：生图前自动拉起 | 服务层状态 |
| `POST /config/idle-timeout` | 设置闲置 N 秒后自动让出显存 | 后台守护线程 |
| `GET /status` | 显存详情（谁在用/剩多少）| 已有，可增强 |

### 闲置自动让出

- 服务层记录 `last_activity`（最后一次生图时间）
- 后台守护线程定期检查：闲置超过 N 秒 → 自动 `unload` 或 `exit`
- N 可配置（默认待定，如 300 秒）

### 与 llama-server 的协作（关键）

llama-server 由另一个 AI 进程管理，我们只管理 ComfyUI：
- **llama 要跑时**：调 `POST /comfyui/exit`（或等闲置超时自动让）
- **我们要生图时**：服务层自动拉起 ComfyUI（llama 侧需自行配合让出，属于另一个进程的职责）

## 四、后续：显卡资源调度器（长期设计目标）

用户提出：需要一个「守护 + 分配」角色，守护显卡资源（有限），协调多个服务（请求多）。

```
┌─────────────────────────────────────────┐
│          显存调度器（守护/分配者）          │
│  - 记录各服务显存占用                      │
│  - 按优先级/请求分配显存                   │
│  - 空闲超时自动回收                       │
│  - 请求冲突时协商让渡                      │
└─────────────────────────────────────────┘
        │ 调度指令            │ 状态上报
        ▼                     ▼
   ComfyUI（生图）       llama-server（聊天）
```

依赖本方案的两项能力：**主动释放内存 + 退出进程**。

### 待决策点

1. 卸载粒度：`unload`（进程保留，重载快）vs `exit`（进程退出，重载慢）—— 都要？还是只要 exit？
2. 闲置超时默认值：多少秒？（如 300s = 5 分钟无生图请求自动让出）
3. 调度器形态：独立进程？还是并入服务层？
4. 优先级策略：生图 vs 聊天，谁优先？
5. 是否做「预约机制」（如 llama 声明要用 → ComfyUI 提前让出）？
